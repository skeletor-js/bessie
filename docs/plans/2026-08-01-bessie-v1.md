## Release decision

The current `0.1.0-rc.3` candidate is the **foundation preview**, not the complete Bessie V1.

Real V1 is:

1. the verified native Herdr/libghostty foundation;
2. a compatible Herdr runtime included in the signed Bessie app, with onboarding and Trouble;
3. Native Bessie Projects that materialize reusable launch recipes as ordinary Herdr workspaces.

The release promise is:

> Download Bessie on an Apple Silicon Mac with no Herdr installation, open it, choose or create a Project, review any startup commands, receive a real Herdr workspace, and quit Bessie without stopping the work.

The component implementation plans are:

- [`2026-08-01-bundled-herdr-runtime-setup.md`](2026-08-01-bundled-herdr-runtime-setup.md)
- [`2026-07-31-native-bessie-projects.md`](2026-07-31-native-bessie-projects.md)

This plan governs their sequence and the integrated release gate. When a component plan conflicts with this plan, this V1 plan controls scope; the component plan controls implementation detail.

## Product boundary

- Herdr remains the runtime and authority for sessions, workspaces, tabs, panes, terminals, processes, agents, and durable live state.
- Every visible terminal remains a real libghostty surface attached to a Herdr-owned pane.
- Bessie may distribute/select a compatible Herdr executable and own versioned Project recipes.
- A Project is launch configuration, never a durable shadow workspace.
- Quitting Bessie never terminates Herdr or successfully launched pane processes.
- Bessie uses only Herdr's public JSON API, CLI wrappers, and public terminal-session bridge.

## Release slices

### Slice A — Preserve the foundation

The verified `0.1.0-rc.3` substrate remains the baseline:

- authoritative snapshot reconciliation;
- workspace/tab/pane mutation;
- real libghostty terminals;
- shell and supported-agent launch;
- Herd, attention, notifications, and command routing;
- controller recovery, reconnect, and process survival;
- compatible local and currently supported remote connection behavior.

Do not reopen or rewrite stable foundation architecture merely because V1 scope changed.

**Exit:** current checks remain green before feature work starts, and every later milestone preserves them.

### Slice B — Bundled runtime, onboarding, and Trouble

Implement the narrow release from the bundled-runtime component plan:

- include the exact compatible Apple Silicon Herdr executable in `Bessie.app`;
- verify artifact release provenance separately from the later compatibility/protocol source baseline, plus SHA-256, version, protocol, redistribution terms, nested signing, and notarization behavior;
- use the included runtime by default while preserving explicit compatible system/custom choices;
- start or reuse only Bessie's named `bessie` session;
- use ordinary Herdr configuration/state conventions without silently editing them;
- provide a short first-run path to one real terminal;
- provide typed read-only Setup Doctor findings and a dedicated Trouble surface;
- preserve honest failures and owner-routed recovery actions.

The initial release does not include an independent runtime updater or automatic configuration repair.

**Exit:** a clean Mac user with no Herdr installation can install Bessie and reach one working real terminal, and a controlled failure is understandable through Trouble.

### Slice C — Native Bessie Projects

Implement the narrow first release from the Projects component plan:

- native versioned JSON recipes under Bessie's Application Support directory;
- catalog, search, create, edit, preview, duplicate, archive, and confirmed delete;
- folder, tabs, pane topology, labels, split ratios, and optional reviewed startup commands;
- exact returned-ID materialization through Herdr's public API;
- connection-specific transient launch tracking;
- structured partial failure with no automatic retry or rollback;
- save an authoritatively observable live workspace shape as a reviewed Project draft;
- command-palette, keyboard, accessibility, and native UI coverage.

The initial release excludes Herdr Plus import, worktrees, remote Project opening, repository-shared recipes, secrets, and automatic matching/reuse of live workspaces.

**Exit:** a local Project can be authored and opened into an ordinary Herdr workspace, and the result survives Bessie quitting.

### Slice D — Integrated V1 hardening

Exercise the complete promise from a clean-machine state:

1. install Bessie with no system Herdr;
2. launch and validate the included runtime;
3. create or choose a Project;
4. review exact startup commands;
5. create the expected Herdr workspace, tabs, panes, labels, ratios, and command output;
6. quit and relaunch Bessie;
7. confirm Herdr processes survived and Bessie reattached;
8. attach through ordinary Herdr tooling;
9. exercise one controlled runtime failure and one partial Project failure;
10. inspect native onboarding, Projects, progress, partial-recovery, and Trouble screenshots.

**Exit:** the clean-machine acceptance test, existing foundation suite, packaging/signing checks, and installed-app identity checks all pass.

## Implementation order

1. Preserve and verify the foundation baseline.
2. Run bundled-runtime Milestone 0: redistribution, artifact, signing, Gatekeeper, and configuration ownership proof.
3. Implement bundled-runtime Milestones 2–6; Milestones 0 and 1 supplied the verified packaging foundation.
4. Run Projects Milestone 0: creation-result, cwd, input-readiness, disconnect, and cancellation contract proof.
5. Implement Projects Milestones 1–6.
6. Run integrated V1 hardening and hands-on acceptance.

Milestones may be implemented through separate goal loops. Do not put the entire V1 backlog into one autonomous goal.

## Validation

After every meaningful checkpoint:

```bash
./scripts/check.sh
```

For native, live-runtime, UI, packaging, installation, and release checkpoints:

```bash
./scripts/mac-verify.sh
```

The Mac verifier must continue to:

- use isolated test configuration/state/socket paths;
- avoid reusing, stopping, or mutating unrelated Herdr sessions;
- build and test Swift code;
- package and sign `dist/Bessie.app`;
- install `/Applications/Bessie.app` after a passing change;
- verify the installed executable matches the packaged executable;
- exercise live Herdr and libghostty behavior;
- inspect native screenshots;
- clean up only the resources it created.

## V1 acceptance criteria

V1 is complete only when all are true:

1. A fresh Apple Silicon Mac user with no Herdr installation can install and open Bessie.
2. The included runtime's artifact, checksum, version, protocol, architecture, signature, and required notices are verified.
3. Bessie starts or reuses only its named `bessie` session and leaves unrelated sessions untouched.
4. Onboarding reaches one real interactive libghostty terminal without terminal setup.
5. Existing compatible Herdr users can explicitly choose a system/custom runtime without Bessie modifying it.
6. Trouble accurately identifies runtime, configuration, API-socket, terminal-socket, controller, and pane failures from observed facts.
7. A user can create, edit, preview, duplicate, archive, and delete a native Project.
8. Opening a Project creates exact Herdr-owned topology using returned IDs rather than labels or guesses.
9. Startup commands are shown exactly before launch, are not interpolated, and use a proven public input-readiness path.
10. Partial Project failures expose the surviving workspace and never auto-retry, auto-close, or fake rollback.
11. Save-current-workspace captures only authoritative facts and requires review before persistence.
12. Ordinary Herdr tooling can inspect and attach to the resulting session/workspace.
13. Quitting and reopening Bessie preserves processes and reconverges from a fresh Herdr snapshot.
14. Existing foundation behavior and tests remain intact.
15. The publicly distributed app passes release signing, notarization, quarantine/Gatekeeper, installation, and relaunch verification.

## Pause conditions

Stop and ask Jordan before proceeding if:

- Herdr redistribution rights or required notices are unclear;
- bundling requires modifying or forking Herdr;
- release signing/notarization requires account or certificate decisions;
- protocol 17 cannot provide exact creation IDs or a reliable headless command-input path;
- a Project requirement would persist live Herdr state or secrets;
- a milestone requires weakening existing checks;
- implementation would overwrite unrelated user configuration or stop unrelated processes;
- the current release-candidate baseline has an unexplained regression.

## Explicit non-goals

- Complete graphical parity with Herdr
- Independent Herdr runtime updates or rollback slots
- Automatic configuration repair
- Generic graphical approvals inferred from terminal text
- Worktrees
- Herdr Plus runtime dependency or synchronization
- Remote Project opening
- Repository-shared Project recipes
- Secrets management
- Generic editor/browser/file explorer/task system
- Broadcast, activity history, normalized plans, cost, or review-and-land cockpit
- Publishing, pushing, merging, or tagging without Jordan's separate explicit approval

## Stop condition

Stop the V1 implementation program only when every acceptance criterion above has real verification evidence, or when a pause condition requires Jordan's decision. Compilation alone, a screenshot alone, or a plausible-looking report is not completion.
